# Module 3 — Orders & Checkout

**Status:** Complete and tested (40 tests in `orders/tests.py`).

## Goal

Convert a cart into an order safely, preserve historical pricing, enforce
valid state transitions, and prevent duplicate orders on double-submit.

## App: `orders`

### Models

| Model | Key fields | Notes |
|---|---|---|
| `Address` | `customer` (FK), `label`, `full_address`, `city`, `pincode`, `phone_number` | |
| `Order` | `order_number` (unique, `ORD-YYYYMMDD-XXXXX`), `customer`/`restaurant` (`PROTECT` — an order must always resolve to a real customer/restaurant), `status`, `delivery_address` (FK), `subtotal`/`discount_amount`/`delivery_fee`/`tax_amount`/`total_amount` (all `Decimal`), `coupon` (nullable FK), `idempotency_key` | `unique_together (customer, idempotency_key)` |
| `OrderItem` | `order` (FK), `food_item` (FK, `SET_NULL`), `food_item_name` (**snapshot**), `price_at_purchase` (**snapshot**), `quantity` | `line_total` property = `price_at_purchase * quantity` |

`order_number` is generated by `generate_order_number()` in `save()` — 5
random-suffix attempts against a uniqueness check before widening to an
8-character suffix, so it's PK-independent and human-readable.

### State machine

`Order.ALLOWED_TRANSITIONS` is an explicit adjacency map:

```
PLACED           -> {ACCEPTED, REJECTED, CANCELLED}
ACCEPTED         -> {PREPARING, CANCELLED}
PREPARING        -> {OUT_FOR_DELIVERY}
OUT_FOR_DELIVERY -> {DELIVERED}
DELIVERED / REJECTED / CANCELLED -> {}  (terminal)
```

`order.transition_to(new_status)` raises `InvalidStatusTransition` for
anything not in the map — there's no silent no-op path. The API layer
(`OrderStatusUpdateView`) catches that and returns `400` with the
exception's message.

### Business rules

- **Checkout is one atomic transaction.** `CheckoutView.post()`:
  1. Requires an `Idempotency-Key` header and an `address_id` — `400` if
     either is missing.
  2. Fast-path: if an order already exists for `(customer,
     idempotency_key)`, returns it directly with `200` — no new order,
     no duplicate side effects.
  3. `transaction.atomic()`: locks the cart (`select_for_update()`) and
     every `CartItem` + its `FoodItem` (via `select_related` under the
     same lock), so a concurrent price/availability change or a second
     simultaneous checkout of the same cart blocks until this one
     finishes.
  4. Empty cart → `400`. Any unavailable item → `400` with the list of
     unavailable item names.
  5. Computes `subtotal`/`total_amount`, creates the `Order`, bulk-creates
     `OrderItem`s copying `food_item_name` and `price_at_purchase` from
     the *current* `FoodItem` state — this is the snapshot the whole
     "historical pricing" requirement hinges on.
  6. Clears the cart items and resets `cart.restaurant = None`.
  7. **A nested savepoint around the order-create step catches
     `IntegrityError`** from the `(customer, idempotency_key)` unique
     constraint — if a second request with the same key won a race and
     committed first, this request returns *that* order instead of
     erroring. This is the actual double-submit protection, on top of
     the fast-path check in step 2 (which only catches the non-racing
     case).
  8. `send_order_confirmation_notification.delay(order.id)` and
     `expire_unaccepted_order.apply_async(..., countdown=300)` are fired
     **after** the `with transaction.atomic()` block exits — never
     inside it — so a rolled-back checkout never queues a notification
     or an expiry timer for an order that doesn't exist.
- **Price snapshot is permanent.** Changing `FoodItem.price` after an
  order exists never touches `OrderItem.price_at_purchase` on existing
  orders — there's no code path that re-reads `FoodItem.price` for an
  already-created `OrderItem`.
- **Ownership.** `get_orders_queryset()` branches by role: customers see
  their own orders, restaurant owners see orders for their restaurant,
  admins see all. `OrderStatusUpdateView` additionally requires
  `CanUpdateOrderStatus` (restaurant_owner on their own restaurant, or
  admin).

### API Endpoints

| Method | Endpoint | Access |
|---|---|---|
| POST | `/api/orders/checkout/` | customer (`Idempotency-Key` header required) |
| GET | `/api/orders/` | customer (own) / restaurant_owner (their restaurant's) / admin (all) |
| GET | `/api/orders/{id}/` | customer (own) or owning restaurant_owner |
| PATCH | `/api/orders/{id}/status/` | restaurant_owner (own restaurant), admin |

### Query optimization

`get_orders_queryset()` applies `select_related("customer",
"restaurant")` and `prefetch_related("items__food_item")` for both the
list and detail views, so serializing order items never triggers an N+1.
